# Test migration

This file tracks the move of the old test suite (`_DRAFT/tests`) to the current project. It lists every old test, what to do with it, and whether it has been migrated.

- **Source:** `_DRAFT/tests`. It has 88 spec files and 550 tests once the loops are expanded.
- **Target:** `tests/` in this repository, built on the current layers (`core` → `api` → `dataset` → `fixtures`).
- **Status legend:**

  | Mark | Meaning |
  |---|---|
  | ⬜ | to migrate |
  | ✅ | migrated |
  | 🔶 | ported, waiting for a run against a freshly seeded platform |
  | 🔀 | merged into another test (named in the decision) |
  | ❌ | dropped (reason in the decision) |
  | ➡️ | moved to another suite |

  The **Decision** column is the plan. The **Status** column is the progress, updated as tests land.

**What "Decision" means:**
- **Migrate**: port as is, on the new fixtures.
- **Parameterize**: becomes one row of a table-driven test, together with the tests named in the decision.
- **Merge → X**: its assertions move into test X, and it disappears.
- **Move → suite**: the check belongs to another API. One UI test stays where the decision says so.
- **Drop**: it duplicates another test or asserts nothing.
- **Isolate**: it changes global platform state, so it runs in a separate serial project.
- **Fix first**: the old test has a defect (vacuous assertion, race, fragile window) that must be fixed while porting.

## Decisions

1. **Who the REST administration tests run as:** the dataset store administrator (`acme_store_administrator@acme.com`, a platform administrator). Tests that lock, delete or change the password of the acting user create their own user with `arrange.security.platformUser()`.
2. **Customer accounts:** a test that changes a customer's own state (cart, lists, addresses, locks) creates its own customer with `arrange.customers.customerAccount()`; read-only checks use dataset users. There are no user pools.
3. **Global state:** the tests that change platform-wide settings or availability live in the `isolated` project. It exists only with `RUN_DESTRUCTIVE_TESTS=true`, runs one worker, and is run on its own, after the other suites.
4. **Known issues:** a test that documents a defect calls `knownIssue(KNOWN_ISSUES.x)` (`fixtures/known-issue.ts`); an entry in `dataset/known-issues.ts` with a tracker key makes the test an expected failure, and one without a key skips it as `fixme` until a ticket exists.
5. **Same-organization account visibility (open):** a plain `org-employee` can read the full account (email, roles, contact id) of any user in the same organization through the GraphQL `user` query; outside the organization the platform answers `Forbidden` (G-contacts-48). Ask the platform team whether this is intended. If it is, add a positive "a colleague's account is readable" test; if not, add a test expecting `Forbidden`, marked as a known issue.

## Status

Every old test is migrated, merged, moved or dropped, except four that wait for a tracker key: B-pagebuilder-19/20, R-platform-86 and R-store-02 (⬜). Tests skipped as known issues say so in their decision.

**Rules for new and changed tests:**
- Ids, SKUs, slugs and user names come from the dataset: a spec may name a dataset id as a constant and reads the rest through `dataset.products.get(...)` and the like.
- Ids are found by search criteria, never by "is listed in the first N / take 1000" windows.
- Prefer table-driven tests over copied ones.
- A UI test checks the UI. Data rules (search semantics, prices, scopes, validation) are checked once through the API.
- Every test that changes data registers its own cleanup, before the change; "leaves data" needs a reason in the test.
- Waits for search-index reads use `INDEX_LAG_TIMEOUT_MS` and belong in `arrange`, not in the test.
- No bare `test.fail` or `test.fixme`: a known defect goes through `knownIssue` and `KNOWN_ISSUES`.
